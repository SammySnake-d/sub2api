## 订正（2026-09-16，取代上面被划掉的那条）

原文写的是：

> resin 的代理口只监听 `127.0.0.1:2260`，外网不可达（已验证）

**这句话是错的，两个分句都错。** 真实情况：

- resin **监听 `0.0.0.0:2260`（全网卡）**，两台机器都是。实测：
  - agcn(124.221.206.59)：`ss -tlnp` 显示 `LISTEN *:2260`，
    启动日志 `Endpoint default starting on 0.0.0.0:2260`。
  - loon(45.205.28.160)：同样 `LISTEN *:2260`。
- **外网可达**。从 loon 直连 agcn 实测 `http://124.221.206.59:2260/healthz` → **200**。
  2260 现已由运营者主动在腾讯云安全组放行，用于访问 resin 控制台。
- 挡在前面的**从来只有腾讯云安全组**，不是绑定地址。同一组实测里
  sub2api 的 8080 口（`ss` 显示同样监听 `*:8080`）从 loon **连不上** ——
  证明安全组是唯一的那道闸，而它是按端口逐个放行的。

当前 2260 的真实暴露面（从外部 vantage 实测，非推断）：

| 探测 | 结果 |
|---|---|
| `GET /healthz` | 200（无需凭据） |
| `GET /ui` | 302（跳登录） |
| `GET /api/v1/platforms` 无 token | **401** |
| `CONNECT` 无凭据 | **407** `Proxy-Authenticate: Basic realm="Resin"` |
| `CONNECT` 错凭据 | **403** |

所以现在真正把关的是 **resin 自己的 token**，不是网络层。这跟原记录以为的
「靠绑回环」是两套完全不同的安全模型 —— 前者的强度等于 token 的强度，
token 一旦泄漏，全网都能拿这台机器当代理用。

### 这个错误是怎么产生的（方法论，值得单独写下来）

当初的验证方法是**「从外部连不上」→ 结论「绑定地址是回环」**。

这是拿**必要条件冒充充分条件**。「绑回环」确实蕴含「外部连不上」，
但反过来不成立 —— 能让外部连不上的原因至少有三类：

1. 绑定地址是回环；
2. 防火墙/安全组拦截（**本例的真实原因**）；
3. 中间链路不通、探测路径本身写错。

一个阴性探测结果同时兼容这三者，它把三个世界压成同一个观测，
因此**无法**用来区分。要断定绑定地址，必须去看绑定本身
（`ss -tlnp` / 启动日志 / `/proc/<pid>/net`），那才是对应的观测量。

更糟的是这个错误是**朝危险方向**错的：它让人以为有一道本不存在的网络边界，
于是不会再去关心 token 强度和安全组规则 —— 而那两样才是真正在承重的东西。

同类反例就在本次排查中又撞了一次：第一次探 6699 时 `/healthz` 返回 000，
差点记成「6699 被挡」；换成 `GET /` 立刻 200。**一次阴性探测只说明这次没拿到，
不说明目标不存在** —— 探测路径写错和目标被挡，在返回码上长得一模一样。

### 顺带修掉的配置真 bug

`agcn:/etc/resin.env` 里写的是 `LISTEN_ADDRESS=127.0.0.1` / `PORT=2260`，
**少了 `RESIN_` 前缀，resin 根本不读**（真源：`internal/config/env.go`，
全部配置键都走 `RESIN_` 前缀）。所以配置文件看起来像「只监听回环」，
实际用的是默认值 `0.0.0.0` —— 配置与行为不一致，且是往危险方向不一致，
这正是上面那句错话能长期不被发现的温床：**读配置文件会读出错误的安全感**。

已改成 `RESIN_LISTEN_ADDRESS=0.0.0.0`（显式写明运营者的决定：监听全网卡、
由安全组控制访问），让配置说的和实际做的一致。差分实证前缀规则：

```
RESIN_LISTEN_ADDRESS=127.0.0.1 → Endpoint default starting on 127.0.0.1:22601   （键生效）
LISTEN_ADDRESS=127.0.0.1       → Endpoint default starting on 0.0.0.0:22604     （键被忽略）
```

## 新事实：出网拓扑已改（2026-09-16）

sub2api 的 **143 个账号现在全部走海外 resin `45.205.28.160:2260`（loon）**，
不再走本机。库里逐条核过，不是抽样：

```sql
select p.host,p.port,count(a.id) from proxies p
  join accounts a on a.proxy_id=p.id group by 1,2;
--  45.205.28.160 | 2260 | 143      （active 143）
select count(*) from accounts where proxy_id is null;  -- 0
```

即 143/143 指向 loon，0 个指向本机，0 个裸奔。

**改的原因**：国内机探不到出口。运营者实测的那一轮是 5000 个节点里只有 **0.9%**
能探到出口 IP（hysteria2 **166 个全灭**、trojan **19 个全灭**、
vless **527 个只活 30 个**），而海外那台健康出口 IP 有 **1888 个**。

本次独立复测（口径不同，节点池已涨到 2.4 万 / 1.7 万，故分母对不上运营者那一轮，
但方向与量级一致，按协议分列）：

| 协议 | agcn 探到出口 | loon 探到出口 |
|---|---|---|
| hysteria2 | 3/323 = **0.9%** | 382/432 = **88.4%** |
| trojan | 12/1214 = **1.0%** | 259/443 = **58.5%** |
| vless | 101/6203 = **1.6%** | 3265/4809 = **67.9%** |
| 合计 | 705/24758 = **2.8%** | 6048/17061 = **35.4%** |
| 健康(断路器闭合)出口 IP 去重 | **104** | **1849** |

loon 侧健康出口 IP 去重 1849，与运营者记的 1888 是同一个量在不同时刻的读数
（租约与熔断持续变动，这个数天然会漂），不是两个互相矛盾的事实。

**对本条判据的影响**：上面那张暴露面表测的是 agcn:2260。loon:2260 同样
`LISTEN *:2260` 且对外可达 —— 它现在承载全部 143 个账号的出网，
**暴露面从一台变成了两台**，两台都只靠 token 把关。

## 复验（本次订正后）

- agcn `systemctl is-active resin` → active，`Endpoint default starting on 0.0.0.0:2260`
- loon `systemctl is-active resin` → active
- 143 个账号抽 12 个用库里真实凭据实打：**11 个拿到出口 IP，1 个失败**

## 结论

第一条（`Proxy-Authorization`）不受影响，仍然通过。

第二条**降级重判**：事实记录这件事本身没做到 —— 原记录写进去的是一条
**错的**暴露面事实，而且错在让人更放心的方向。订正后才算真正满足
「后果显式记录在此」。现在的真实结论是：
**2260 与 6699 都对公网开放，唯一的边界是 resin token 与 sub2api 的 key，
网络层只有安全组按端口放行这一层。**


## 机器核不到的那一半

「明文 HTTP 的风险是否可接受」是运营者的判断，不是机器能判的。
这份记录只保证下一个接手的人不会以为这里有 TLS。
