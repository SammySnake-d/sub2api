## 核对内容

两条判据：(1) 没有一个出口 IP 归属 CN 或 HK；(2) 没有一个等于 VPS 自身公网 IP。
第二条比第一条更危险 —— 它长得像「代理配好了」，实际请求在裸奔。

## 怎么做的

不是抽样，是把 resin 的**全部活跃租约**拉下来逐条核：

```
GET /api/v1/platforms/00000000-0000-0000-0000-000000000000/leases
GET /api/v1/geoip/lookup?ip=<每一个出口 IP>
```

### 但原记录有一句推断是**错的**，必须撤掉

> 真正持续成立的是那条约束（订阅源里不含 CN/HK 节点），不是这一份名单。

**订阅源里含 CN/HK 节点。** loon 当前池子实测：健康(断路器闭合)且探到出口 IP 的节点里，
**cn 42 个、hk 54 个，去重出口 IP 合计 96 个**。原记录从「名单里没有 cn/hk」
反推出「源里没有 cn/hk」—— 又一次拿观测当机制（与 proxy-auth-and-exposure.md 里
「连不上 ⇒ 绑回环」同型的错误：阴性观测兼容多种机制，不能挑一个当结论）。

**真正在承重的机制是平台级 region 过滤器**，不是订阅源干净：

```
platforms.region_filters_json
  loon / Paid    = ["!cn","!hk"]     ← 143 个账号走的就是这个平台
  loon / Default = []                ← 没有过滤器
  agcn / Default = ["!cn","!hk"]
```

这条订正是**加强**而不是削弱判据：真实机制是一条显式的、可读可测的配置，
比「碰巧源里没有」可靠得多。但它也带出一个原记录看不见的风险 ——
**loon 的 `Default` 平台没有 region 过滤器**，任何走 `Default` 而非 `Paid`
的调用方都不受 cn/hk 约束。这一点原来的推断会让人完全想不到去查。

### 另一句需要限定作用域

> 超过 3 个账号的 IP：**0 个**（`max_leases_per_ip=3` 逐条成立，不是配了就算数）

观测没错，但**归因只对 agcn 成立**。现在承载 143 个账号的 loon 上，
这个配置值是 **`max_leases_per_ip = 6`**，不是 3。loon 当前实测每 IP 账号数分布
`{1:177, 2:7, 3:2}`、最大 3、超 3 的 0 个 —— 看起来还是「不超过 3」，
但那是**当前分布碰巧如此**，不是那条上限在挡。按 loon 的真实配置，
合规上限是 6；拿「最大 3」去证明「cap=3 生效」在这台机器上属于无效推理。
